# Design

## Context

The repo has no frontend yet. This change adds `frontend/`, an Angular app that talks only to the FastAPI service defined by `backend-api` (change `add-backend-api`). That service runs the same LangGraph pipeline as the CLI (`agent-workflow`), so the browser only reads state and sends commands. All decisions, payments, and validation of the reviewer and releaser names happen on the server, and the client repeats the name and rationale checks only so the user gets feedback right away. The case's one-day guideline, combined with a second stack, makes build cost the main constraint; see proposal.md, Why.

## Goals / Non-Goals

**Goals:**
- A single shared table component and a single shared name field, so the six pages stay consistent and quick to build.
- Pages work on polling before SSE exists, so frontend work isn't blocked on F29.
- A data layer that can switch from polling to SSE without touching any page component.

**Non-Goals:**
- Login, roles, or server-side identity. Names are typed by hand.
- Offline/PWA support, i18n, and a dark theme beyond Material's default palette.
- Any business rule in the client, such as outcome, amount, or duplicate logic.

## Decisions

**Angular 18 standalone components with Angular Material and RxJS.** The source spec fixes this choice. Material supplies the sidenav, table, sort, paginator, dialog, snackbar (toasts), chips, badges, and stepper-like primitives. Using NgModules was rejected because standalone components with lazy-loaded routes per page keep each page self-contained.

**Routing.** There is one route per page: `/` (Home), `/queue`, `/audit`, `/review`, `/payment-queue`, `/payments`. The detail drawer is driven by a `?invoice=<id>` query param, so a drawer can be deep-linked and the browser back button closes it.

**Layout.** `MatSidenav` uses `mode="side"` at 960 px and wider and `mode="over"` below, where the sidenav shows icons only. The switch is driven by `BreakpointObserver` with a custom `(max-width: 959.98px)` query rather than Material's preset breakpoints, which don't land at 960.

**Data layer: one `LiveStore` service per resource behind an `ApiClient`.**
- `ApiClient` wraps `HttpClient`, with typed DTOs mirroring `backend-api` responses. It is generated by hand from the backend's OpenAPI document rather than through a codegen dependency.
- Each store exposes `rows$`, built as `merge(refresh$, poll$ or events$)` → `switchMap(fetch)` → `shareReplay(1)`. Pages subscribe with the `async` pipe.
- P0: `poll$` is `timer(0, 3000)`, paused while `document.hidden` to cut load.
- P1 (F29): an `EventStreamService` opens one `EventSource` to `/api/events` and maps each event type to the stores it invalidates. For example, `invoice.stage_changed` invalidates the queue store and stats, and `batch.finished` invalidates the payment queue, payments, and stats. While the stream is open, polling stops. On `error` the service falls back to `poll$` and retries the stream with backoff.
- The alternative was refetching a page's data inside each component, which would duplicate timers and make the SSE switch touch every page.

**Badges and footer** come from `/api/stats` through the same store mechanism, shared by the shell. The footer's provider and model come from the backend. They come from the `llm` field of `/api/stats` (defined in `add-backend-api`).

**Shared `InvoiceTableComponent`.** It takes column definitions (key, header, cell template ref, sortable flag), a row stream, and a `rowClick` output. It owns `MatSort`, `MatPaginator`, the search box (client-side filter over visible cell text), and the status chip. Server-side paging was rejected because the prototype sees dozens of invoices, not thousands. The Audit's expandable timeline row and the Payment Queue's selection column are content projections into the shared component, not forks of it.

**Status chips.** A single `STATUS_STYLE` map (status → label, color, icon) is the only place status colors are defined, which guarantees the "same color on every page" requirement.

**Name field.** `ReviewerNameFieldComponent` is a `ControlValueAccessor` with a validator that trims and requires a length of 1 to 50, plus a characters-left hint. It reads and writes `localStorage['acme-ipa.reviewer-name']` inside try/catch. The review dialog and the pay dialog both use it, and the stored name is written only after the server accepts a decision.

**Dialogs.** Two components are used. `ReviewDecisionDialog` has a mode of approve, reject, credit-confirmed, or reject-revision. `PayConfirmDialog` has a scope of all, selected, or one row. Each disables confirm until the form is valid and shows a spinner while the request is in flight. On 409, the review dialog shows "Already decided by someone else" and triggers a refresh of the review store, while the pay dialog shows "A batch is already running."

**Toasts** use `MatSnackBar` through one `ToastService`. Batch-summary toasts are triggered by a `batch.finished` event, or under polling by noticing a new entry in `/api/payment-batches`. The revision-swap toast fires when the queue store sees a row of kind `replacement` arrive whose original row just left the queue.

**Upload.** The drop zone and Browse both feed a single `UploadService.add(files)`. Extension, 10 MB, and empty-file checks run first, then each valid file is sent as its own multipart POST to `/api/invoices` with `reportProgress: true`, at most 3 concurrently. One request per file was chosen over a single multi-file request so each row gets its own progress bar and its own error. The `.eml` extension is allowed by the picker even though the provided data has no `.eml` files, per the spec.

**Detail drawer (P1, F30)** is a right-side `MatSidenav`. Text formats (TXT, CSV, JSON, XML, EML) render in a `<pre>` fetched from `/api/invoices/{id}/file`. A PDF renders through `<object type="application/pdf">` pointed at a blob URL, with a download link as the fallback.

**CSV export (P2, F35)** links to `/api/invoices.csv` or `/api/payments.csv` with the current filter's query params. No CSV is generated in the browser.

**Dev setup (P1, F33).** A repo-root `Makefile`:
- `setup` runs `pip install -e backend[dev]`, `npm ci --prefix frontend`, and the `data-model` seed command.
- `dev` runs uvicorn and `ng serve` together with a trap that kills both on Ctrl+C.

`ng serve` uses a `proxy.conf.json` that sends `/api` to the backend. That avoids CORS in development, although the backend still allows the dev origin. `docker compose up` is optional and covers the same two services.

**Frontend tests (P1, F32).** Component tests use the Angular CLI's default Karma/Jasmine runner, so no extra test framework is introduced. Playwright e2e lives in `frontend/e2e/` and runs against `make dev` with `LLM_PROVIDER=offline` and a freshly seeded DB.

## Risks / Trade-offs

- [Angular plus Python roughly doubles build time] → Material for every widget, one table component, polling before SSE, and pages built in spec order so a partial app still demos.
- [Client-side search and paging won't scale] → Acceptable for the prototype. The shared table is the single place to switch to server-side paging later.
- [Polling every 3 s from several stores multiplies requests] → All stores share one `timer` tick, and polling pauses while the tab is hidden.
- [The revision-swap toast is inferred from list diffs under polling] → It is exact once SSE `payment.cancelled` / `payment.queued` arrive. Under polling the toast may lag one tick, which is harmless.
- [localStorage can be blocked in private windows] → Wrapped in try/catch, so the name field simply starts empty.
- [Playwright depends on deterministic backend outcomes] → Run in offline mode against a reseeded DB, with INV-1010 as the known NEEDS REVIEW case.

## Migration Plan

This is greenfield with nothing to migrate. Rollback means removing `frontend/` and the Makefile targets. The CLI keeps working without the web app.

## Implementation notes

- **Versions (pinned exactly):** Angular 18.2.14 / CLI 18.2.21, Angular Material + CDK 18.2.14, RxJS 7.8.2, TypeScript 5.5.4, `@playwright/test` 1.48.2, `material-icons` 1.13.12 (icon font served locally so the app works offline).
- **Layout:** `frontend/src/app/core` (DTOs mirroring `backend/src/acme/api/queries.py`, `ApiClient`, `LiveStore`/`PollTicker`/`Stores`, `EventStreamService`, `NotificationsService`, `UploadService`, `ToastService`), `shared` (`InvoiceTableComponent`, `STATUS_STYLE` + chip, `ReviewerNameFieldComponent`, stage strip, format pipes), `pages`, `dialogs`, `detail` (drawer + rationale timeline), `shell`.
- **Live data:** every store is `params$ → merge(tick$, refresh$) startWith → switchMap(fetch)`, `shareReplay({refCount: true})`. The shared tick waits one period on first start and fires at once on resume (tab visible again, or SSE dropped). While SSE is connected polling is off; event invalidations are coalesced for 100 ms, and every store refreshes on (re)connect because the backend sends a `ready` event and does not replay.
- **Toasts:** batch summaries fire from `batch.finished` or from a newly finished row in `/api/payment-batches` (batches finished before the app opened are ignored); revision swaps fire from the Payment Queue diff (replacement row appears, lower revision of the same invoice leaves). `payment.queued` carries no `revision`, so the event only triggers the refresh and acts as a 1.5 s fallback toast. Ids are remembered so each toast fires once.
- **Statuses:** `STATUS_STYLE` also includes `Revised`, which the backend's audit view returns for runs whose revision was paid as a delta.
- **Audit filters** (status, dates, `search` from the Payments "audit entry" link) are server-side so the CSV link uses the same params; the table's search box is client-side. The Payments footer sums the rows currently matching both the server filters and the table search.
- **Tests:** Karma uses `CHROME_BIN`, else Playwright's Chromium (`karma.conf.js`), with `--no-sandbox`. 48 component/unit specs. The Playwright e2e (`frontend/e2e`) starts its own offline backend on a fresh DB (port 8100, idle auto-pay off) and its own `ng serve` (4300), so it never touches dev data.
- **Dev setup:** `make setup` prefers `uv` for the venv and install (falls back to `venv` + `pip`); `make dev` uses `trap 'kill 0'` so Ctrl+C stops both servers. `docker-compose.yml` uses stock `python:3.14-slim` and `node:22-slim` images with bind mounts; the frontend container proxies to `backend:8000` via `proxy.docker.json`.
