# Design

## Context

See proposal.md - Why. This change assumes the earlier changes are implemented: Pydantic models and `acme.db` tables (`data-model`), the `get_chat_model(role)` factory and offline `RuleBasedLLM` (`llm-provider`), `audit_log`/`llm_calls` writers (`audit-logging`), the parsers and normalizers, the validation tools and rules engine, and the payment queue and executor (`payment-processing`). This change composes them; it does not re-implement any check, rule, or payment logic. Layout follows the shared contract: package in `backend/src/acme/`, repo-root `main.py` shim, tests in `backend/tests/`.

## Goals / Non-Goals

**Goals:**
- One compiled graph used unchanged by the CLI and, later, by `backend-api`.
- Deterministic, offline golden suite that runs in CI-like conditions with no network.
- Held invoices survive process restarts.

**Non-Goals:**
- HTTP endpoints, upload worker, schedulers (add-backend-api).
- Batch trigger timing (end of day, idle); the CLI only runs explicit batches.
- Recorded Grok/Claude fixtures (F34, P2) — the golden suite here runs offline only.

## Decisions

**Graph shape.** `backend/src/acme/graph/build.py` exposes `build_graph(checkpointer)` returning a compiled `StateGraph(InvoiceState)` with nodes `ingest`, `normalize`, `validate`, `validation_tools` (a `ToolNode`), `approve`, `critic`, `review_hold`, `disposition`. Conditional edges: `ingest` loops to itself while `retries < 2` and validation fails, else routes to `normalize` or (on failure) `disposition`; `validate` ⇄ `validation_tools` until no tool calls, then a deterministic `run_all_checks` merge; `approve` → `critic` → `approve` until pass or 2 rounds; `approve` → `review_hold` when NEEDS_REVIEW, else `disposition`. Alternative: hand-written orchestrator — rejected because the case scores framework use and LangGraph gives `interrupt()` and checkpointing for free.

**Deterministic merge after the tool loop.** Rather than trusting the LLM's tool choices, the validate node calls every check function after the loop and dedupes findings by `(code, evidence key)`. This enforces handoff rule 2 with one code path in both offline and LLM modes.

**Floor enforcement in one place.** A `stricter(a, b)` helper over the ordering REJECT > NEEDS_REVIEW > APPROVE is applied when `approve` reads each draft; any loosening attempt is clamped and recorded as a trace event `llm_override_blocked`. Keeps rule 3 and 4 testable as a unit.

**Human review via `interrupt()`.** `review_hold` calls `interrupt({...summary})`; the graph is compiled with `SqliteSaver` on `acme.db` (separate checkpoint tables managed by `langgraph-checkpoint-sqlite`), and `thread_id = run_id`. Resume uses `Command(resume={"decision","reviewer","rationale"})`. A shared `acme.workflow.resume_review(run_id, decision, reviewer, rationale)` validates input, claims the run with a conditional `Awaiting review → Resuming` update in `BEGIN IMMEDIATE` (zero rows → `ReviewConflict`), writes `review_decisions`, and then resumes the graph; for holds of kind `payment_failure`, whose graph has already ended, it calls `payment-processing`'s `resume_payment_failure` instead. The CLI and API both call it, so the rules live in one place. `recover_orphaned_runs()` resets runs found mid-pipeline at startup to Uploaded and returns them, so a crash never blocks the idle payment trigger; the API re-enqueues them. Alternative: persist our own pending table and start a new run on decision — rejected because it splits one invoice across two runs in the audit trail.

**Runner API.** `acme.workflow.run_invoice(path, provider=None) -> RunResult` and `run_folder(dir)` (sorted by filename) wrap invoke + `invoice_runs` status updates. The CLI calls only these, so `backend-api` reuses them verbatim.

**CLI.** `argparse` in `backend/src/acme/cli.py` keeps the README's exact `--invoice_path=` form while supporting subcommands `payments run`, `review`, and the `--explain` flag; `rich` renders a live stage status and a results table. `--json` disables rich and writes JSON lines to stdout; logs go to stderr. The repo-root `main.py` shim comes from `add-project-foundation`; this change replaces the stub `acme.cli.main()`. Alternative: Typer — rejected because mixing `--invoice_path=` top-level options with subcommands is simpler in argparse.

**Golden tests.** `backend/tests/test_golden.py` uses a session fixture that seeds a temp `acme.db`, runs `run_folder("data/invoices")` with `LLM_PROVIDER=offline`, then one `run_batch(trigger="pay_all", released_by="test")`. A parametrized test over the 20-row table asserts outcome, finding codes (subset match), and paid amounts. The EUR row asserts USD = 4,125.00 × configured rate ($4,455.00 at the default 1.08), and the batch total is $37,620.00. The CLI's `--pay` and `payments run` use trigger `pay_all` with `released_by` `cli`.

**Golden dependency on P1.** Several golden rows need P1 features from other changes: INV-1010's NEEDS REVIEW (F12), INV-1003's `FRAUD_SUSPECTED` and INV-1005's `SUSPICIOUS_ADDRESS` (F11), INV-1012's `NEAR_THRESHOLD` (F11), and INV-1014's PAID with `CURRENCY_CONVERTED` (F7). Decision: keep those features P1 and stage the golden suite. Those five rows carry `xfail(strict=True)` tagged with the feature they need, so P0 ends with a green suite (15 passed, 5 xfailed) and each tag must be removed as its feature lands. With P0 only, INV-1010 is auto-paid and INV-1014 is held, so the per-file counts are asserted only once no row is tagged. Revision and adversarial cases build files in `tmp_path` from copies of `invoice_1004.json` and `invoice_1001.txt`.

## Risks / Trade-offs

- [Offline extraction regex can't handle a new messy layout] → golden suite only covers provided files; LLM providers handle the rest, and failures fail closed with `EXTRACTION_FAILED`.
- [Checkpoint tables in the same `acme.db` could lock under concurrent writes] → WAL mode on connection; the CLI runs invoices sequentially. The API change revisits concurrency.
- [Golden order dependence (duplicates, revision) makes tests coupled] → order is explicit (sorted filenames) and asserted in a dedicated scenario; unit tests cover each piece independently.
- [Subset match on finding codes could hide extra wrong findings] → additionally assert that no CRITICAL finding appears on the 7 paid files.

## Open Questions

- Default `released_by` for CLI batches is `cli`; the spec's trigger list has no CLI-specific value, so CLI batches record `pay_all`. Can be revisited without changing behavior.

## Implementation notes

- **Dependencies.** `langgraph~=1.2`, `langgraph-checkpoint-sqlite~=3.1`, `rich~=15.0` (pytest was already a dev extra).
- **Graph shape (deviation).** `acme.graph.build_graph(checkpointer)` compiles `StateGraph(WorkflowState)` with nodes `ingest`, `normalize`, `validate`, `approve`, `disposition`, `review_hold`: ingest → normalize | disposition; normalize → validate | disposition (no invoice); validate → approve → disposition; disposition → review_hold (when held) | END; review_hold → disposition. The three loops are not re-implemented as graph edges: the extraction self-correction loop runs inside `ingest()` (F4), the validation tool loop plus deterministic sweep and dedupe inside `run_validation()`, and the Approval ⇄ Critic loop with the `stricter()` clamp inside `run_approval()`. The nodes call those capabilities unchanged, so there is no separate `validation_tools`/`critic` node and no second retry counter. The design's `llm_override_blocked` trace event is the existing `approval.clamped` event (source, proposed, final, floor). `WorkflowState` = `InvoiceState` + `source_format` + `hold_kind`.
- **Review hold.** Disposition records the hold (`record_processed`, `supersede_original` if REVISION, `enqueue_review`) and then routes to `review_hold`, whose only job is `interrupt()`, so replaying the node on resume has no side effects. Resume returns to `disposition` with the reviewer's `Decision` (`decided_by` = reviewer, rules + `HUMAN_REVIEW`). Hold kind is `credit` when `REVISION_OF_PAID_INVOICE_LOWER_TOTAL` fired (details carry `overpaid`), else `warning`; hold details also carry `findings`, `ai_recommendation`, `ai_rationale`. An approved credit hold resolves `Credit confirmed` (no payment, for add-backend-api task 4.3); a rejected one resolves Rejected. If `queue_payment` itself returns `held`, the run pauses the same way.
- **Checkpointer.** `open_checkpointer()` opens its own `check_same_thread=False` connection to `settings.db_path` in WAL mode, with `JsonPlusSerializer(allowed_msgpack_modules=...)` listing the `acme.models` types (avoids langgraph's "unregistered type" deserialization warning). `compiled_graph()` opens one per call and closes it, so every resume rebuilds the graph from disk; `thread_id = run_id`.
- **Runner API (`acme.workflow`).** `create_run(path, stored_path=None) -> run_id` (status/stage `Uploaded`); `process_run(run_id, provider=None, on_event=None) -> RunResult` (continues an unfinished checkpoint, leaves a paused run alone); `run_invoice(path, provider=None, on_event=None)` = both (raises `FileNotFoundError` first); `run_folder(dir, provider=None, on_event=None) -> list[RunResult]`; `run_state(run_id) -> WorkflowState | None`; `list_reviews()`; `recover_orphaned_runs() -> list[run_id]`. Review: `record_review(run_id, decision, reviewer, rationale)` (validation → `ReviewInputError`; `BEGIN IMMEDIATE` claim `Awaiting review → Resuming` → else `ReviewConflict(.status)`; `review_decisions` insert; `reviewer/review.decision` audit), `continue_review(run_id, on_event=None)` (resumes with the latest stored decision; payment-failure holds go to `resume_payment_failure`), and `resume_review(...)` = both. The API can record synchronously and continue on its worker; `continue_review` also re-submits runs left `Resuming` after a crash.
- **Statuses written.** Nodes set `status = Processing` with `stage` Extracting (ingest), Validating, Deciding; disposition tools write `Queued for payment`, `Awaiting review`, or `Resolved` (final Paid, Revised, Rejected, Duplicate, Superseded, `Credit confirmed`); a claimed review is `Resuming`. `on_event(name, data)` (a context var, so nothing is stored in the checkpoint) receives `invoice.stage_changed` and `invoice.resolved`.
- **Fail closed.** If the validation LLM fails, `run_checks` plus `detect_duplicate` still run (`validation.fallback`); if the approval LLM fails, the policy floor decides and VP scrutiny becomes NEEDS_REVIEW (`approval.fallback`); any other unexpected exception records a REJECT (`workflow.failed`) so no run is left mid-pipeline.
- **CLI.** `--verbose` added (INFO JSON logs on stderr; default is WARNING, and `--json` always logs INFO to stderr). The CLI seeds an empty `acme.db` on first use, so the README command works from a clean checkout. At startup it runs `recover_interrupted_batch()` and re-processes runs from `recover_orphaned_runs()`. `payments run` with nothing payable prints "Nothing is queued" without creating a batch record. In `--json` mode `mock_payment`'s print goes to stderr. `review` output is a block per held invoice rather than a table (long rationales).
- **Golden suite.** `backend/tests/test_golden.py`: all 20 rows pass offline; F7, F11, F12 had already landed, so `NEEDS_FEATURE` is empty (the strict-xfail staging and the count-assert skip were verified by re-tagging one row) and the count assert (7 paid, 1 superseded, 1 held, 11 rejected, 3 duplicates) runs. Batch total $37,620.00.
- **Cross-module fixes.**
  - `acme.validation.checks._paid_amount` (validation): `RevisionContext.paid_amount` summed only the previous revision's ledger rows; it now sums every revision up to the original's (delta rows included), matching `acme.payments`. Test: `test_paid_amount_sums_every_earlier_revision_and_delta`.
  - `acme.validation.checks.reconcile_math` (validation): a difference of exactly $0.01 was treated as within tolerance, contradicting this change's "total off by one cent → MATH_MISMATCH" scenario. Now only sub-cent differences are tolerated (amounts are cent-quantized, so any cent is a mismatch). The earlier test asserting the opposite was updated (`test_one_cent_off_is_flagged_sub_cent_is_not`). Extraction's F4 line-sum check is unchanged, so a one-cent TXT error reaches validation and is rejected as `MATH_MISMATCH`.
